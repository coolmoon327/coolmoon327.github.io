论文不只是一份排版完成的 PDF。它还包括从证据到论断、图片、引用、源文本和构建过程的完整链条，这条链应当能被合作者或未来的自己检查。VS Code 与 LaTeX 的价值，在于让这条链更清晰，而不是把编辑器配置得越来越复杂。

## 从论断与证据开始

润色文字之前，先建立“论断—证据”映射。对每项计划中的贡献，记录支撑它的分析、图片、实验、定理、数据集或一手文献，并明确区分观测结果、个人解释与工作局限。这种做法能比逐句修改更早暴露缺乏支撑的表述。

阅读优秀论文是为了理解学科惯例，真正写作时则应依据自己的证据表和笔记。不要复刻另一篇论文的句子顺序，也不要只替换其措辞。逐字摘录的笔记应始终带有明显引号和来源，直到它被正确引用或彻底删除。这样既保护原创性，也保留了回溯证据的可靠路径。

## 把论文视为可构建项目

将正文、文献库、图片与构建说明放在一个小而清晰的目录结构中：

```text
paper/
├── main.tex
├── sections/
├── figures/
├── references.bib
├── README.md
├── .gitignore
└── .vscode/
```

优先使用 LaTeX 的语义结构——章节、标签、交叉引用、引用命令与可复用宏——而不是手工模仿视觉格式。[LaTeX Project 官方文档](https://www.latex-project.org/help/documentation/)比复制来的零散格式片段更适合作为语义参考。

README 应说明预期的 TeX 发行版、编译引擎、参考文献后端、入口文件、必要字体或外部工具，以及唯一的构建命令。如果出版模板规定了特定流程，就应明确记录这项约束，而不是把它藏在某台电脑的编辑器设置里。

## 让自动化驱动构建

[LaTeX Workshop 的构建文档](https://github.com/James-Yu/LaTeX-Workshop/wiki/Compile)以 recipe 管理构建，并默认选择 `latexmk`。这比维护一串手工 LaTeX 与文献编译命令更可靠：[latexmk](https://ctan.org/pkg/latexmk)会观察依赖关系，并重复调用所需工具，直到文档达到最新状态。

编辑器只应作为一个通用命令的前端；同一命令离开 VS Code 也必须能够运行：

```bash
latexmk -pdf -interaction=nonstopmode -file-line-error main.tex
```

命令成功退出只是必要条件。还要检查日志中的未定义引用、缺失文献、字体替代、越界排版框以及过时或缺失的图片。凡是可能改变含义或版面的警告，都应按构建失败处理。

## 让文献库可审计

使用一份经过审阅的 `references.bib` 作为唯一权威文献库。[BibTeX](https://ctan.org/pkg/bibtex) 记录便于导入，但导入数据并不天然可信。引用之前，应对照出版社页面或其他权威记录核对作者顺序、标题、期刊或会议、年份、页码与 DOI。

引用键应稳定、易读，并避免为同一工作的预印本与正式发表版本留下重复记录。如有 DOI 或正式出版链接，应予以保留。更重要的是，让引用紧邻它真正支撑的论断；在一大段文字末尾堆叠若干弱相关文献，并不能形成证据链。

## 用 Git 记录决策

忽略临时构建产物，而不是论文证据：

```gitignore
*.aux
*.blg
*.fls
*.fdb_latexmk
*.log
*.out
*.synctex.gz
```

某些投稿系统会要求一并提交参考文献输出等生成文件。此时应单独归档投稿包，或有意识地加入所需产物；不应让一条笼统的忽略规则替你决定哪些文件属于正式记录。

提交之前，同时检查工作区和实际补丁。[Git status 文档](https://git-scm.com/docs/git-status)解释了工作区、暂存区与已提交内容之间的区别。

```bash
git status --short
git diff --check
git diff --cached
```

提交应小而明确，说明一次学术决策，例如“修改评估协议”“修正图片来源”或“按审稿证据统一论述”，而不是只写“更新论文”。每次投稿都应打标签或另行归档，使当时的 PDF、源文件、文献库和结果能够被一起恢复。

## 明确可复现目标

对于日常协作，“可复现”至少应意味着：从干净检出版本出发，使用一条有文档记录的命令，就能依据已标识的输入重建论文中的论断、表格和图片；仍需人工完成的步骤必须逐项记录。

逐字节一致是更强的目标，可能需要固定的 TeX 发行版或容器、精确的软件包与字体版本、受控时间戳以及确定性的图片生成过程。只有归档或合规需求确实值得时，才引入这套机制；未固定版本的本地环境不能宣称实现了精确复现。

## 发布前检查

投稿或公开发布之前：

1. 从干净检出版本构建，不要依赖长期使用的工作目录。
2. 解决缺失引用、文献、图片以及重要版面警告。
3. 确认每个非平凡事实论断都能追溯到数据、分析或一手引用。
4. 确认每张图片均可重新生成，或具有完整的来源说明。
5. 审阅完整 Git 差异，确认没有私密笔记、凭据或临时数据进入版本。
6. 归档实际提交的源文件包与 PDF。

这套流程通过消除隐藏状态来提高写作效率。更重要的是，它让最终论文经得起检查：每项论断都有来源，每个版本都有历史，每次构建都有明确路径。
